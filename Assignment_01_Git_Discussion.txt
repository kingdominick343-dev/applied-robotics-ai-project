PROJECT CONTEXT
The planned project is an educational desktop camera-tracking demonstrator
with a C-RAM-inspired appearance and no projectile-launching mechanism.
The first stage will use the laptop webcam and laptop-based Python/OpenCV
processing. An existing ESP32 is intended to control a future pan/tilt
assembly. An ESP32-CAM is a later purchase and camera upgrade.

The laptop webcam is fixed to the laptop: turning the separate assembly
does not turn that camera or automatically center its view. Begin with
on-screen object tracking; validate the mechanics separately. A later
camera mounted on the platform enables camera-following experiments.
The ESP32-CAM upgrade does not by itself make vision processing standalone;
the laptop remains the planned processing host unless later tests justify
a change.

An ESP32 and 3D printer are available according to the project discussion.
Two positional servos, a suitable separate regulated supply, mounting parts,
and an optional servo driver remain planned hardware; purchases and exact
specifications need confirmation. The earlier MG996R/PCA9685 suggestions
are candidates, not validated selections.

Planned milestones: define scope and test object; verify webcam capture;
prototype on-screen tracking; confirm hardware; validate ESP32 and mechanics;
design and print the frame; integrate and evaluate; then assess ESP32-CAM.
Implementation and hardware tests are not yet recorded as complete.

1. ADD: SELECT CHANGES FOR THE NEXT COMMIT
After creating or editing a file, its changes exist in the working directory.
The command "git add <file>" copies that file's current changes into Git's
staging area. Staging lets me choose exactly which changes belong together.
It does not create a commit or upload anything to GitHub. If I edit the file
again after staging, I must add it again to include the later changes.

Example:
  git add README.md
  git diff --staged

2. COMMIT: RECORD A LOCAL SNAPSHOT
The command "git commit" records the staged changes in the local repository's
history. Each commit has an identifier and a message describing the change.
Meaningful messages make the development history easier to understand.
A commit is stored locally; creating it does not automatically send it to
GitHub. Unstaged changes are not included in a normal commit.

Example:
  git commit -m "Document workspace setup and project workflow"

3. PUSH: SHARE COMMITS WITH THE REMOTE REPOSITORY
The command "git push" sends local commits and updates the corresponding
branch on a remote repository, such as GitHub. This makes committed work
available remotely for backup and collaboration. It requires network access
and permission to write to the repository. It does not upload uncommitted
working files. If the remote has diverged, I should fetch and integrate its
changes before retrying rather than force-pushing without understanding why.

Example for the first push of a feature branch:
  git push -u origin docs/workspace-demo

THE DIFFERENCE
Add selects the changes. Commit records those changes locally. Push shares
the resulting commits remotely.

  Working directory -> git add -> staging area
  Staging area -> git commit -> local repository history
  Local repository -> git push -> remote repository on GitHub

Add and Commit can be used offline. Push needs access to the remote.
Git is the version-control tool; GitHub hosts a remote Git repository.

4. CLONE, EDIT AND BRANCH: DEMONSTRATION WORKFLOW
The following commands are a demonstration guide, not a claim that they
have already been executed. Run them in a terminal during the video.

Clone creates a local working copy, including repository history, and sets
the source repository as the remote named "origin":
  git clone https://github.com/kingdominick343-dev/c-ram-desktop-tracker.git
  cd c-ram-desktop-tracker
  git remote -v

Create and switch to a separate branch:
  git switch -c docs/workspace-demo

Edit README.md in a text editor, adding a short, accurate progress note.
Save it, then inspect, stage, commit and push:
  git status
  git diff
  git add README.md
  git diff --staged
  git commit -m "Add verified workspace demonstration progress"
  git push -u origin docs/workspace-demo
  git log --oneline -5

Open GitHub and create a pull request from docs/workspace-demo into main.
Review the changes before merging, and link the pull request to the related
Trello card. Use a different branch name if this branch already exists.
